# Supabase 준비 단계 보안 검토

2026-10-26 / `feat/supabase-auth-foundation`. 직접 검토이며 독립 리뷰가 아니다.

## 변경과 통제

- 기존 ID/사번 로그인 계약을 유지하며 서버 전용 Auth 매핑을 사용한다. 실제 이메일·전화번호는 사용하지 않는다. 관리자만 발급·비밀번호 변경·권한 설정한다.
- 웹 HttpOnly/SameSite 쿠키, 모바일 메모리 bearer 세션. DB에는 세션 토큰 해시와 암호화된 Auth access token만 저장한다. 매 요청 Auth 사용자·활성 상태·세션 버전을 확인하며 인증 서비스 장애 시 차단한다.
- 관리자 API와 SQL RPC가 각각 현재 sysadmin 권한을 검사한다. 프로필/매핑 생성은 한 트랜잭션, Auth 생성 보상 삭제, 비밀번호 변경 전 잠금·세션 폐기, 실패 시 비활성 유지, 마지막 관리자 보호 및 감사 기록을 구현했다.
- AS 소유자 UUID/관리 권한 검사를 서버에서 적용한다. 이름만 같은 사용자는 편집할 수 없다. 기존 이름 기반 소유권은 별도 검증 매핑이 필요하다. 최신 main에서 제거된 공정·ERP·지도·모바일 앱·SSE는 복원하지 않았다. 공정 권한 배열은 이전 참고용으로만 보존한다.
- 프로필 자기 조회 RLS, private 식별자/세션 접근 금지, 비공개 Storage 경로 및 AS 권한 정책. 파일 다운로드는 직원 JWT로 RLS를 적용한다.
- 최신 main의 AS/첨부 출력 인코딩, DOM 이벤트 처리, 첨부 URL 인코딩 및 CSP를 보존하고 실제 브라우저에서 회귀 검증했다.
- 루트 npm audit 취약점 0건. 최신 main의 불필요한 xlsx/Expo 의존성 제거를 유지하고 Supabase SDK 및 PGlite만 추가했다.

## 검증 결과

- `npm test`: 68개 통과, 실패 0개. 인증·AS·사용자관리 및 삭제 API 회귀 테스트.
- `npm run test:xss`: 실제 Chromium 기반 브라우저 1개 통과. CSP 활성/비활성 양쪽에서 악성 AS/제품/첨부 문자열이 실행되지 않음을 확인했다.
- 공식 Supabase SDK → loopback 모의 Auth/PostgREST/Storage → 실제 Express HTTP 경로: 웹/모바일 로그인, 내 프로필, 비로그인·권한 부족·위조·비활성·만료·세션 변경·서비스 장애 차단.
- PGlite PostgreSQL에서 SQL 세 파일을 실행: RLS/함수 권한/불변 ID/Storage 정책/마지막 관리자/발급 매핑/비밀번호 잠금·복구 검사. Supabase 시스템 스키마는 최소 모형이다.
- 관리자 모듈: 입력 검증, Auth 생성 보상, 비밀번호 실패 잠금. 테스트는 임시 폴더와 합성 데이터만 사용한다.
- 실제 Supabase, 모바일 실기기, HTTPS 프록시 연동은 미검증이다. 모바일 앱 복원 없이 HTTP bearer 계약을 검증했다.

## 남은 작업과 한계

1. 실제 검증 프로젝트 SQL 적용, Auth 내부 주소/가입 차단, Storage API/RLS 통합 검증. 운영 DB에는 적용하지 않았다.
2. AS 업무 DB 이전, UUID 매핑, 파일 업로드/메타데이터 보상 처리와 악성 파일 검사. 현재 AS 업무 저장은 JSON이며 동시 쓰기·충돌 및 백업 복구는 별도 개선이 필요하다.
3. 장애 시 pending 재설정 운영 복구와 고아 Auth 정리. 절차는 `supabase-local-setup.md`에 있다. 감사 조회 UI와 관리자 작업 재인증은 후속 작업이다.
4. 로그인 응답 시간 기반 계정 추정은 완전히 검증하지 않았다. 로그인 제한·프록시 관측, 만료 세션/제한기 청소가 필요하다.
5. 전체 화면 침투 테스트와 실기기 검증을 대신하지 않는다. 브라우저 CDN 의존성은 npm audit 범위 밖이다. Node 22 이상이 필요하다.

안전한 설정과 이전 계획은 `supabase-local-setup.md`, `supabase-transition-plan.md`를 참조한다. 실제 데이터 이전·운영 배포는 수행하지 않는다.
