# AS 보안 보강 적용·복구 유의사항

2026-11-01. 활성 직원 모두의 AS 공동 작업 정책과 남은 소스 기반 보강을 함께 적용한다. 실제 운영 서버·Supabase에는 이 변경으로 접속하거나 마이그레이션을 적용하지 않았다.

## 바뀌는 동작

- AS 검토·승인 설정과 작성자 제한을 제거한다. 비활성·익명 접근, 사용자 관리의 sysadmin 제한, 변경 사유와 버전 충돌 검사는 유지한다. 신규 로컬 계정의 active:false를 보존한다.
- 누적 workflow.history는 현재 접수에 한 번 저장한다. 신규 event before/after와 request result 스냅샷은 `record-history-v1`과 count로 해당 시점의 접두 이력을 참조한다. 응답 시 이를 복원하여 과거 값과 재시도 결과를 보존한다. 삭제 건도 보존되므로 참조는 끊기지 않는다. 기존 전체 스냅샷과 새 참조가 섞인 파일도 읽는다.
- 과거 이벤트에 이미 중복 저장된 이력을 일괄 삭제·변환하지 않는다. 이력 조회는 기본 50건/최대 100건으로 나누며, offset으로 다음 페이지를 조회한다. 시간순 이벤트·현재 history를 운영자가 임의 삭제·재정렬하지 않는다.
- PDF는 문서당 12쪽/15초, 작업당 20문서·40쪽·48M 픽셀·PNG data URL 24MiB/45초, 단일 canvas 8M 픽셀을 한도로 처리한다. 한 문서가 실패·초과하면 일부 페이지를 정상 인쇄처럼 내보내지 않고 해당 PDF 전체를 제외한 안내를 표시한다. 원본 첨부 다운로드는 유지한다. 다중 접수 인쇄도 예산을 공유한다.
- 새 미리보기·닫기는 이전 PDF 작업을 취소하고 Blob URL을 해제한다. PDF.js 내부 파싱·동기 PNG 인코딩을 OS 수준에서 선점하는 기능은 아니므로 별도 렌더러 격리나 실제 브라우저 자원 한도 검증을 대체하지 않는다.
- Supabase 로그인은 비밀번호 확인 전에 직원 UUID/Auth UUID·role·session_version을 읽고 이후 값과 비교한다. 최종 세션 발급 RPC는 같은 직원 행을 잠근 상태에서 active·reset 진행 여부·UUID·role·버전을 다시 확인한다. 인증 공급자가 이전 JWT를 계속 인정하더라도 재설정을 가로지른 새 앱 세션은 거절한다.

## 검증 근거와 한계

작은 합성 이력 8/16/32회 변경에서 저장 파일은 기존 69,358 / 183,702 / 567,526 bytes에서 37,464 / 68,607 / 130,895 bytes로 감소했다(시간·ID에 따라 소폭 달라질 수 있다). 과거 스냅샷과 재시도 결과가 동일함을 확인했다. 이는 운영 용량·지연·고갈 시험이 아니다. 전체 JSON을 읽고 쓰는 저장 구조와 영구 감사 기록의 선형 증가는 남아 있으므로 장기 보존·총량·DB 이전 계획은 별도 운영 과제다.

인증 테스트는 실제 SDK/로컬 HTTP 대역과 PGlite를 사용한다. 비밀번호 검증 직후 및 프로필 읽기 직후에 reset 완료·진행·실패를 끼워 넣고 거절을 확인한다. 실제 Supabase 버전의 JWT 폐기 정책이나 다중 DB 연결의 잠금 대기는 확인하지 않았다. PDF 테스트는 작은 합성 문서/API 대역과 실제 canvas/DOM을 사용하며, 외부 라이브러리 다운로드·실제 첨부·부하 시험은 하지 않는다.

## 운영 적용 순서

1. 릴리즈 승인 시 정확한 태그/SHA와 호환되는 런타임·SQL을 함께 확정한다. 업무 JSON/첨부 영구 저장소와 DB 백업 및 복구 절차를 확인한다. 실제 비밀 설정을 코드·PR·로그에 복사하지 않는다.
2. 별도 검증 환경에서 기존 001~003 뒤 `202611010004_shared_as_access.sql`, `202611010005_login_epoch.sql`을 순서대로 적용하고 직원/중지 계정/익명 및 관리자 역할을 검사한다.
3. 005는 service_role의 app_sessions 직접 INSERT를 회수한다. 새 런타임은 새 RPC가 없으면 로그인 실패하며, 이전 런타임도 005 이후에는 로그인 실패한다. 무중단 혼용을 가정하지 말고 짧은 로그인 중지/유지보수 시간에 SQL과 런타임을 함께 적용·검증한다. 기존 로그인 세션도 적용 후 확인한다.
4. 이번 푸시·PR 생성은 운영 적용을 의미하지 않는다. PR 병합, 릴리즈 및 운영 배포는 각각 승인 흐름을 따른다.

## 복구

- AS JSON은 참조 스냅샷을 해석하는 런타임이 필요하다. 이전 런타임으로 코드만 내려가면 과거 이력/재시도 응답을 올바르게 복원하지 못한다. 구버전 복구는 적용 전 데이터 백업 또는 검증된 참조 해제 변환본을 함께 준비하고 변경 이후 데이터 손실 가능성을 먼저 검토한다. `.bak`은 직전 세대일 뿐 적용 전 백업을 대신하지 않는다.
- 004 복구는 기존 002의 `private.staff_can_manage_as` 본문을 CREATE OR REPLACE로 복원한다. 기존 permission 열·값은 보존되어 있다. 002 전체를 재실행하지 않는다.
- 005 복구에서 이전 런타임을 사용하려면 보호된 DB 변경으로 service_role의 app_sessions INSERT 권한도 되돌려야 한다. 새 RPC를 단순 제거하거나 권한만 변경하는 식의 불완전 복구는 피한다. 구버전 로그인 경합 방어가 사라지는 점을 고려해 검증된 수정 버전을 우선한다.
- 코드·권한 롤백은 이미 수행한 AS 변경이나 계정 비밀번호를 자동 복원하지 않는다.

## 실제 환경에서 별도 확인할 항목

배포된 인증 모드, TLS/프록시/CORS/원본 접근, DB migration/RLS 실제 적용, Storage bucket 접근, Auth 정책, 백업·복구, 유지보수/보존 작업. 운영 테스트 금지 조건을 지키기 위해 이 환경을 확인했다고 주장하지 않는다.
