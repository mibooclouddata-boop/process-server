# AS 접수 무결성 보강

현재 JSON 저장소를 보강한 변경이다. Supabase DB/Storage 이전, 운영 데이터 변환, 배포는 수행하지 않는다. 인증은 기존 서버의 검증된 세션과 계정 권한을 사용한다.

기준 브랜치의 Supabase 인증 준비와 직원·첨부 메타데이터 스키마는 유지한다. `AUTH_PROVIDER=supabase`에서도 이번 AS 본문 저장 경로는 JSON이다. 아래 DB 요구사항은 기존 스키마에 본문·번호·재시도·이력을 추가하는 후속 이전에 적용한다.

## 적용한 보장

| 영역 | 처리 방식 |
| --- | --- |
| 식별자·접수번호 | 신규 ID는 UUID. 서울 시간 기준 월별 번호를 잠금 안에서 배정한다. 저장된 카운터와 기존 번호의 최댓값을 함께 확인하고 삭제한 번호도 재사용하지 않는다. 기존 중복 ID/번호는 자동 변경하지 않고 요청을 차단한다. |
| 재시도 | 모든 쓰기에 `Idempotency-Key`가 필요하다. 사용자 ID와 키가 같고 요청 내용·첨부 SHA-256이 같으면 기존 결과를 반환한다. 같은 키의 다른 내용은 409다. 접수, 카운터, 요청 결과와 이력을 하나의 JSON 교체로 저장한다. |
| 저장 실패 | 같은 디렉터리에 임시 파일을 쓰고 fsync한 뒤 rename한다. 이전 세대를 `as.json.bak`에 보존한다. 읽기·쓰기 모두 배타 잠금을 사용한다. 손상된 파일을 빈 목록으로 바꾸지 않는다. |
| 동시 수정 | 내용, 비고, 파일 연결, 진행 상태, 삭제, 복원 모두 공통 `version`을 비교하고 증가시킨다. 누락은 428, 오래된 값은 409다. 충돌한 내용을 덮어쓰지 않는다. |
| 입력 | 호선·블록·사유는 공백만 있는 문자열을 금지하고 길이와 타입을 검증한다. 구분은 허용 목록만 받는다. 금액은 미입력(null) 또는 0~9,007,199,254,740,991의 정수 원 단위다. 날짜는 실제 존재하는 YYYY-MM-DD이며 0000년은 거부한다. |
| 진행 | 기존 순차 단계와 완료일 순서를 유지한다. 실제 작업일은 접수 입력일보다 앞설 수 있으나 미래 또는 이전 단계 완료일보다 앞설 수 없다. 진행 중·완료 건의 납품 협의일을 비울 수 없다. 완료 건 정정에는 사유가 필요하다. |
| 권한 | 조회는 로그인한 계정에 허용한다. 변경·삭제·복원·이력 조회는 작성자 ID, AS 검토/승인 권한 또는 시스템 관리자에게 허용한다. 이름이 같다는 이유로 소유권을 부여하지 않는다. 작성자와 변경자는 서버가 결정한다. |
| 첨부 | 무작위 저장 이름, 확장자와 기본 파일 시그니처, 크기와 SHA-256을 확인한다. 실패·재전송의 신규 업로드를 정리한다. 로그인 후 살아 있는 접수에 연결된 파일만 다운로드할 수 있다. 파일명은 DOM 텍스트로 표시한다. |
| 이력·삭제 | 변경 전후 값, 사용자 ID/이름, 시각, 버전과 사유를 보존한다. 삭제는 tombstone을 남기며 목록에서 숨긴다. 첨부 해제·접수 삭제는 파일 바이트를 보존한다. |

요청당 파일 10개, 파일당 20MB, 요청 합계 100MB, 접수의 현재 첨부 합계 50개/200MB 제한을 적용한다. 시그니처 검사는 악성코드 검사나 Office 문서의 완전한 구조 검증을 대신하지 않는다. 기존 첨부를 일괄 검사·변환하지 않는다.

## API와 화면 호환성

- 기존 생성/수정/진행/삭제 경로는 유지한다. 쓰기에는 기존 `X-Requested-With: process-server`와 새 `Idempotency-Key`가 필요하다. 키는 16~128자의 영문·숫자·밑줄·하이픈이다.
- 생성 외 쓰기는 `version`을 보내야 한다. 삭제·복원은 1~500자의 `changeReason`도 보낸다. 완료 접수 수정도 `changeReason`이 필요하다. 진행의 기존 revision은 응답 호환용이며 공통 version이 충돌을 판정한다.
- `GET /api/as/:id/history`: 변경 이력. `GET /api/as/trash`: 접근 가능한 삭제 건. `POST /api/as/:id/restore`: 현재 버전과 복원 사유로 복원. 이력·휴지통 전용 관리 화면은 이번 범위에 포함하지 않는다.
- `GET /api/as/requests/:key`: 현재 사용자의 해당 키가 이미 저장되었는지 확인한다. 다른 사용자의 요청 결과는 반환하지 않는다.
- 화면은 같은 작업의 키와 입력 해시만 sessionStorage에 남긴다. 폼 내용은 저장하지 않는다. 응답 유실·로그인 만료 후에도 같은 키로 재시도한다. 결과가 불명확한 상태에서 입력을 바꾸면 서버에서 결과를 확인한다. 이미 저장된 작업을 별도 저장하려면 화면에서 명시적으로 선택해야 한다. 아직 저장되지 않았다면 같은 키를 유지해 먼저 완료된 요청만 적용한다.
- 같은 내용이라도 서로 다른 키를 가진 의도적인 신규 접수는 허용한다. 브라우저 세션을 완전히 종료해 키를 잃은 경우에는 목록에서 결과를 확인해야 한다.
- 이전 화면/외부 API 클라이언트는 새 키·버전 계약에 맞춰 갱신해야 한다. 페이지를 새로 열어야 한다.
- 기존 `createdById`가 없는 접수는 AS 관리자에게 수정을 허용한다. 이름을 통한 자동 연결은 하지 않는다. 원래 작성자에게 돌려주려면 검증된 계정 ID 매핑과 이력을 남기는 별도 데이터 작업이 필요하다.
- 기존 접수 ID/번호/진행 이력은 유지한다. 버전이 없는 접수는 기존 workflow.revision 또는 0에서 시작한다. 과거에 이미 사라진 변경/삭제 이력을 복원하지는 못한다.

## 운영 전환·백업·복구

1. 서버를 중지하고 `PROCESS_DATA_DIR`의 정확한 경로와 `as.json`, `uploads`, 계정 파일을 확인한 뒤 별도 보안 저장소에 함께 백업한다. 환경 변수 미지정 시 코드 디렉터리를 사용하므로 운영에서는 영구 데이터 디렉터리를 지정한다. 잘못 지정한 새 경로는 신규 설치로 인식될 수 있다.
2. 모든 AS writer를 이 저장 모듈을 사용하는 버전으로 맞춘다. 이전 프로세스, 직접 JSON 편집 또는 잠금을 무시하는 도구와 동시에 실행하지 않는다.
3. 중복 ID/접수번호 또는 손상된 JSON이 있으면 원본을 보존하고 별도로 정정한다. 이 버전은 조용히 재번호를 매기거나 백업으로 자동 대체하지 않는다.
4. `as.json.initialized`는 기존 파일 유실을 감지하기 위한 표식이다. 초기화 후 본 파일이 없어지면 503을 반환한다. 표식·백업을 지워 빈 데이터로 재시작하지 않는다.
5. 비정상 종료 후 `as.json.lock`이 남으면 요청은 제한 시간 후 503으로 실패한다. **해당 데이터 경로를 쓰는 모든 프로세스가 종료된 것을 확인한 후에만** 잠금 파일 정보를 확인하고 수동으로 제거한다. 단순히 오래됐다는 이유로 잠금을 빼앗지 않는다.
6. 복구 시 현재 파일·이력·업로드를 먼저 보존한 뒤 검증한 백업을 명시적으로 복원한다. `.bak`는 이전 한 세대이며 별도 장기 백업이 아니다. 백업으로 되돌리면 그 이후 접수와 요청 키도 소실되므로 해당 기간의 저장 여부를 대조한다.
7. 예전 코드로 단순 롤백하면 삭제 건 노출, 영구 삭제, 재시도 중복이 다시 생길 수 있다. 삭제 표식·버전·요청 기록을 이해하는 호환 버전으로 롤백하거나 서비스를 중지한 상태에서 복구한다. 코드만 롤백해서 데이터를 복원했다고 판단하지 않는다.

백업·이력에는 업무 내용과 사용자 식별자가 들어간다. 데이터 디렉터리의 운영체제 접근권한을 제한하고 코드/PR에 포함하지 않는다. fsync/rename의 내구성은 운영체제·파일시스템에 의존하며 디렉터리 메타데이터까지 포함한 전원 장애 내구성은 보장하지 않는다. JSON과 업로드 파일은 하나의 파일시스템 트랜잭션이 아니므로 장애 후 참조와 바이트를 대조해야 한다.

## 남은 파일 정리

`node as-storage-maintenance.js --data-dir <기존 데이터 디렉터리>`는 기본적으로 조회만 한다. JSON을 정상적으로 읽고 잠금을 획득한 뒤, 접수의 현재 첨부와 해제 이력 어디에서도 참조하지 않는 **7일 이상 지난 파일**을 후보로 보여준다. 삭제 접수의 파일과 최근 업로드는 제외한다. 하위 디렉터리나 심볼릭 링크는 순회하지 않는다.

실제 삭제는 검토와 백업 후 같은 명령에 `--apply`를 명시한 경우에만 한다. 운영 경로에서 이 명령을 실행한 적은 없다. 삭제·해제된 첨부의 영구 폐기는 보존 기간과 감사 정책을 정한 뒤 별도로 구현해야 한다.

## Supabase로 이전할 때 필요한 DB 보장

아래는 다음 이전 작업의 설계 요구사항이며 실행한 SQL/마이그레이션이 아니다. JSON 파일 잠금은 단일 호스트의 로컬 디스크를 위한 방어다. 여러 호스트·네트워크 파일시스템이나 지속적인 이력 증가를 처리하는 DB 대안이 아니다. 현재 이력과 재시도 결과는 JSON에서 계속 증가하므로 DB 이전 시 분리·보존 정책이 필요하다.

| 영역 | 필요한 제약조건·트랜잭션·권한 정책 |
| --- | --- |
| 접수 | UUID PK, 접수번호 UNIQUE NOT NULL, 월+순번 UNIQUE, 작성자 FK, version NOT NULL CHECK(version >= 0). 기존 문자열 ID는 별도 legacy_id UNIQUE로 매핑하고 모든 파일·이력 참조를 검증한다. |
| 필수값·금액·날짜 | 필수 문자열 NOT NULL과 btrim 길이 CHECK, category/status CHECK 또는 참조 테이블. 금액은 bigint에 현재 정수 범위 CHECK를 적용하거나 클라이언트 문자열 직렬화를 명시한다. 업무일은 date, 생성/변경 시각은 timestamptz. nullable 필드의 CHECK만으로 NOT NULL을 대체하지 않는다. |
| 번호·재시도 | 월 카운터 행을 원자적 UPSERT/RETURNING 또는 행 잠금으로 증가시킨다. 요청 기록에 UNIQUE(actor_id, idempotency_key)와 payload hash를 둔다. 요청 키 예약, 번호 배정, 접수 저장, 첨부 연결, audit 저장, 요청 결과 확정은 한 DB 트랜잭션으로 묶는다. 실패한 트랜잭션 전체를 같은 키로 재시도한다. |
| 동시 수정·상태 | UPDATE ... WHERE id = ... AND version = expected 형태로 1행만 변경되었는지 확인하고 version을 증가시킨다. 진행 전이는 권한을 검증하는 DB 함수 또는 트리거로 제한한다. 여러 행의 단계 날짜 검증은 다른 행을 읽는 CHECK로 구현하지 않는다. |
| 파일 | attachment의 receipt_id FK와 storage object key UNIQUE. 소유자·접수·업로드 상태를 서버가 연결한다. Storage 업로드와 SQL은 단일 트랜잭션이 아니므로 임시 업로드→검증→DB 연결→확정 및 유실 재조정 절차가 필요하다. private bucket, 서명 URL 또는 인증된 다운로드를 사용한다. |
| 감사·삭제 | append-only audit 테이블에 변경 전후, actor UUID, 버전, 시각, 사유를 서버/트리거가 기록한다. 감사 행 UPDATE/DELETE를 일반 역할에 허용하지 않는다. 접수와 사용자 삭제가 이력·파일을 연쇄 삭제하지 않게 FK 정책을 정한다. 사용자 탈퇴 시에도 식별 이력이 유지되는 profile tombstone 등을 설계한다. |
| RLS·권한 | 모든 노출 테이블에 RLS를 켜고 anon 접근을 차단한다. 현재 공동 업무 조회 범위를 authenticated에 명시하고 쓰기는 작성자·AS 관리자 정책으로 제한한다. 사용자 역할은 사용자가 수정 가능한 metadata에서 읽지 않는다. INSERT/UPDATE의 WITH CHECK까지 적용하고 작성자·상태·version·audit를 임의 변경할 테이블 쓰기 권한은 제한한다. |
| 함수·서버 키 | DB 함수는 기본 security invoker를 우선한다. definer가 필요하면 최소 소유 역할, 고정 search_path, 스키마 명시, 실행 권한 제한과 내부 권한 검사를 적용한다. service_role은 RLS를 우회하므로 브라우저에 두지 않으며 서버 API에서도 별도 권한 검사를 한다. |
| 인덱스·검증 | FK와 RLS 조회 조건을 위한 인덱스, 상태·날짜 조회 인덱스를 실제 쿼리로 검증한다. 이관 전후 접수 수·번호·금액·단계·파일 개수/해시와 고아 참조를 대조하고, 다른 사용자/관리자/비로그인 RLS 검사 및 동시성·재시도 검사를 DB에서 다시 실행한다. |

근거: [PostgreSQL 제약조건](https://www.postgresql.org/docs/current/ddl-constraints.html), [트랜잭션 격리](https://www.postgresql.org/docs/current/transaction-iso.html), [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [DB 함수](https://supabase.com/docs/guides/database/functions), [Storage 접근 제어](https://supabase.com/docs/guides/storage/security/access-control).

## 검증

- `npm test`: 입력, 금액/날짜, 동일 키 재시도, 3개 Node 프로세스의 번호 배정, 공통 버전 충돌, 장애 주입, 파일 정리, 권한, 복원/이력 및 기존 인증/화면 회귀 검사.
- `npm run test:xss`: Chromium에서 CSP 적용/미적용 모두 업무 텍스트·첨부파일명이 실행되지 않는지 확인.
- `npm run test:as-browser`: 실제 저장 뒤 응답을 끊고 같은 폼 재전송, 수정 충돌 시 입력 유지, 삭제 사유, 첨부 접근 차단과 복원 확인.

모든 검사는 별도 임시 디렉터리의 가상 데이터로 실행한다. 실제 업무 데이터·첨부파일은 수정하지 않는다.
